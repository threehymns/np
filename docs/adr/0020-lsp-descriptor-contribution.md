# The host owns the LSP descriptor; the plugin owns the server

Language servers are described to the host and driven by a plugin. Host core gains one contribution type — a descriptor naming a command, its arguments, an ordered list of root markers, and the languages it serves — and nothing else. There is no client, no stdio, no JSON-RPC, no process management and no log buffer in `@np/core`. A bundled LSP Core Plugin owns all of that, plus the document walk that turns a marker list into a directory.

## Why the host stops at the descriptor

The alternative was to host the client and have plugins declare configuration for it. That would put language-server machinery in the same package as the language registry, the command registry and the editor compartments, behind interface names the host would then have to keep stable: `startLanguageServer`, `sendLanguageServerRequest`, `stopLanguageServer`. Those names are Git-shaped, not reusable — the shape of ADR 0008's warning about accumulating feature-specific methods, one layer down. A host that can start a process is a host that cannot be reasoned about as a neutral meeting point, and the second server (a future language pack's first requirement, per spec #263) would arrive as new host surface rather than as configuration.

The descriptor keeps the reusable part reusable. It is data, joined on the language identity the language registry already publishes, so it is a third sibling of `languages.ts` and `completions.ts` rather than a new `EditorContributionType` for the same reason ADR 0019 gives: "start this process against this root" is not a CodeMirror `Extension`. Ownership follows the record, not the transform that ran last, and a duplicate ID is reported rather than resolved — a silently dropped claim would start no server for files someone declared one for.

**The sibling is a claim about the registry's shape, and the method names do not match the siblings'.** `registerLanguage` and `registerSnippet` are named for the thing a plugin contributes; the nine methods this adds carry the feature instead — `registerLspDescriptor`, `rebuildLspDescriptors`, `lspRevision` — which is the shape ADR 0008 warns against, so the tension is recorded rather than smoothed over. The two are not the same objection, which is why it is accepted: 0008's warning is aimed at methods that *do* something a feature needs, which is exactly what `startLanguageServer` and `sendLanguageServerRequest` were rejected for above, whereas every method here is a transform registry's own add, remove, rebuild and read surface — what a registry is, under any name. Dropping the prefix was rejected for the opposite reason: `registerDescriptor` says what is registered without saying what, and a language, a snippet, an editor extension and an LSP descriptor are four different things to a plugin author reading `PluginHostInterface`. So the equivalence claimed above holds for the registry and stays in tension with the interface, and that tension is the thing to reopen: a second feature-prefixed registry on this interface turns an exception into a pattern.

That join key is the registry's *display name*, and the protocol's `languageId` is a different vocabulary: `@codemirror/language-data` publishes the TSX description as `TSX` while the TypeScript server answers to `typescriptreact`. Spelling a descriptor's `languages` with protocol ids therefore looks correct and silently leaves every `.tsx` file claimed by nothing, because nothing joins on `typescriptreact`. Neither registry carries the mapping from one vocabulary to the other, so the descriptor does: `languageIds` is a registry name to protocol id map, materialised empty when a contribution declares none, and a served name with no entry lowercases. That is right for every language whose registry name already is its id and wrong for `TSX` and `JSX`, which is the point — the mapping cannot be derived from the name and must be data. An earlier version of this slice recorded the gap as a known limit instead, on the argument that the field was new descriptor surface; that argument made the second server architecture rather than configuration, which is what the next section is about.

`bundled` is the same argument about the platform side: which package a server ships as, and which script inside it, is descriptor data, so a platform that resolves commands out of its own `node_modules` needs no table of server names of its own. What is left in the resolver is the walk and the two candidate rules, both of which are true of any command.

## The platform is a seam, not an implementation

`LSP_PLATFORM_SERVICE_KEY` names two capabilities `@np/core` cannot have for itself: spawn a process, and ask the filesystem whether a file exists. It does not name an implementation, and the host stores whatever it is given opaquely (ADR 0008). The desktop app supplies it over Electron IPC; the plugin resolves it per use and degrades to "no LSP" when it is absent. That absence *is* the web story: spec #263 puts stdio on desktop and leaves remote and headless hosting to a later spec, so a web build publishes nothing and the plugin stays inert rather than half-working. The manifest says `platforms: ['desktop']` for the same reason, which ADR 0006 permits provided the limit is stated — it is, in the manifest description as well as the field.

Two things made the seam the right shape rather than a `desktop`/`web` split inside the plugin. A real process and a real filesystem then stay testable without either leaking into neutral core: the lifecycle suite spawns the scripted stub server as a genuine child process over genuine pipes, and only the executable is swapped (ADR 0004 makes the same argument for real `git`). And a future remote transport is a new provider behind the same key, not a second client.

## Root markers are descriptor data; the walk is code

The descriptor says *what identifies a project*. The plugin says *how to use it*: from the open document's own directory upward, within a directory the first declared marker present wins, across directories the marker declared first wins overall, ties broken by the nearest directory. A nearer marker therefore does not beat a more specific one — in a repository with a root `tsconfig.json` and a `package.json` in a nested package, a file in that package still resolves to the root its `tsconfig.json` declares. That is what makes the field an ordered list rather than a set, and it is why the host contributes no marker names of its own: a second place that knew what a project was would eventually disagree with the first.

One descriptor attributes each decision. Two descriptors claiming one file is a configuration fault, not a preference: picking by registration order would make the answer depend on which plugin enabled first, so the conflict is reported and no server starts for that file.

## Document sync sends full content

Sync is declared as full-document (`textDocumentSync: 1`) and every change carries the whole text. Incremental sync is the recorded later optimisation, held back until large-file behaviour is actually measured. Sending whole documents is more bytes on the wire and less code that can be wrong about offsets, and nothing in this slice has shown the cost to be real.

## `editor.lsp` gates the document, and the process it leaves empty

The `lsp` setting is per language and it gates **the server for documents of that language**: a document whose language has it off is not scoped to a server, not synced, and not diagnosed. It still gets notes and words. Two shapes were rejected, and the setting's own description was corrected rather than kept, because the old wording — "off leaves words and notes alone" — was true and still let a user read a switch that did not stop anything.

**Per document, not per process.** One descriptor serves `TypeScript`, `TSX`, `JavaScript` and `JSX`, and one process serves all four. So a `.tsx` file with `lsp: false` is declined while a `.ts` file alongside it starts and syncs the same process. A per-process gate would be the same mistake in the opposite direction: turning `lsp` off for TSX would then silence TypeScript as well, and the two are independent answers to independent questions. This is the same argument ADR 0020's `languageIds` makes about registry names versus protocol ids — one entry, several identities, joined per document.

**Turning it off stops a server nothing is served from.** It prevents new starts for that language and stops syncing it — including a `didClose`, so a server still holding the text stops publishing for the file — but it does not tear down a process another document is being served from. That is deliberate and it is a trade: a settings toggle that kills processes other open files depend on is worse than the bug it fixes. What it does do is stop a server that has no enabled document left, and forget it. That is not a different rule at the tail; it is the per-document rule run out, and it is where an earlier version of this decision stopped. "Do not tear down" was carried as an absolute when it only ever needed to mean "do not tear down while something is still being served". The cost was a server serving only disabled languages sitting in the status list with a process and no document attached — which is precisely what a switch that does nothing looks like from the outside, so the trade was protecting one row of a menu against the whole premise of the setting. The stop is an ordinary lifecycle decision with the same pid accounting and the same no-orphan guarantee as an explicit stop from the menu, not teardown inside a settings callback. A stopped-by-the-gate server is *not* marked stopped-by-the-user: turning the setting back on brings it back on the next document event.

**A settings change is an event, because a user does not type to flip a switch.** Reading the gate on every use is not enough on its own. The events that carry a document are typed keystrokes, so a gate that only re-reads when one arrives makes "off" land whenever the user happens to type next — which is indistinguishable from a broken switch, which is the failure this section exists to remove. The runtime therefore subscribes to the settings *change* and re-evaluates there, so the transition happens while the editor sits idle. The re-evaluation is a comparison, not a resolution: the notification says that some setting changed and says nothing about which, so the runtime reads the gate for the documents it is actually syncing, and a change that flips none of them costs two settings reads per document — no root walk, no spawn, no protocol traffic. The subscription is released on disable, because a runtime that outlived it would keep answering settings changes for the rest of the session.

**Resolution is on the way out of the memo.** `LspTargetResolver` memoizes a target per file against the descriptor registry's revision, and a settings change does not move that revision. The gate therefore reads the setting on every use, *outside* the memo — a value cached while `lsp` was on would keep a server running for a language the user has since turned off. What the memo may hold is which server a file belongs to, not whether that server should exist for it.

**The plugin reads the setting itself, because the runtime decides and the document carries the language.** `PluginHostInterface.settings` is `SettingsRegistryLike`, and that is schemas and nothing else — schemas, transforms and the materialized view. Resolved *values* live behind `SettingsResolver` in `SettingsManager`, which the plugin host does not hold and should not, since resolution consumes the schemas rather than being part of the registry. So the app publishes a `settings:reader` service (`SettingsReader`, one `read(namespace, key)` plus an optional `subscribe`) and the plugin resolves it per use through `getService`, degrading to the documented default when nothing is published. The registry's own `subscribe` is the wrong signal and cannot be the right one: it fires on schema registration, which a settings *value* never touches, and a plugin that waited on it would learn that a schema was contributed and never that a user changed their mind. That is ADR 0008's shape — the host names the capability, not the feature — and it is why the gate needed no new seam and no feature name in the shell. The alternative, passing the resolved flag down from the editor, is what the rest of the slice already does for the *completion source* and cannot do here: the value that decides whether to spawn is read in a different package than the one that owns the process.

**One narrowing rule, in the package that owns the keys.** The fold over `editor.languages` and the "only `false` turns a language off" narrowing are one rule read from two places: the source that settles `inactive` and the runtime that declines to start. A cross-package parity test was the obvious answer and the wrong one — two implementations drift no matter how many tests compare them, and the comparison only ever shows the inputs its author thought of. So both live in `@np/core`, beside `scopeForLanguage` and beside the schema that declares the keys: `editorSettingsForLanguage` reads the `editor` namespace for a caller-named list of keys and folds one language's overrides over them, and `editorLspEnabled` does the narrowing. The keys are a parameter because the readers genuinely differ in shape — the completion source resolves four at once, the gate resolves one — and each side still narrows only what it owns. What the module-graph wall that first blocked the parity test was really about is that a UI package cannot import core *source* from a test without dragging `svelte` with it; it turned out to be no obstacle to a shared function, which was the point of having one.

## What is asserted, and where

Story 10 — the second server is configuration against this type — is met for the two places it used to fail. Which packaged dependency a server ships as, and which script inside it runs, are descriptor fields rather than a table in the desktop resolver, so a second bundled server is a second entry in `LSP_DESCRIPTORS`. Which protocol id a served language is synced under is a descriptor field, so a server whose languages do not lowercase to its ids needs no host change. What a second server does *not* get for free is the client's capability declaration: `textDocumentSync`, `completionProvider` and everything else the client claims in `initialize` describe the client, not the server, and are one table in `LspClient` that a second server adds nothing to. Making that per-descriptor would be the wrong shape — it would let a descriptor claim a capability the client does not implement, which is exactly what `resolveProvider: true` would be, since `completionItem/resolve` is not implemented (ADR 0021) — so it stays where it is, and the honest statement of the boundary is that a second server is configuration up to the point where it needs a client capability the client does not yet declare, which is a change to the client and not to the descriptor type. `processId` is the other half of that handshake and is the one claim about the client the client cannot make for itself: the renderer does not spawn the process, so the pid is the transport's to report. The seam carries it, and the client declares what it was given rather than a hard-coded `null`, because `null` is LSP's "I have no process id" and a server given it cannot watch its parent and exit when the editor dies.

The registry's three acceptance properties — remove-one equals a clean build, a mid-session refresh loses nothing and duplicates nothing, deactivate/reactivate equals pre-activation — are asserted on the registry, because that is where replay decides them. Lifecycle claims are asserted against a real process and a real pipe: the root the client resolved is read back out of the stub's own `initialize` reply, and "no orphan" is checked with the pid, not with a flag. The byte-level framing is asserted separately by feeding the parser one byte at a time, because a pipe read that splits a multi-byte character is the case a fake stream cannot produce.

The gate's two edges are asserted the same way, because both are decisions that would otherwise be visible only as a behaviour nobody wrote down. That a settings change acts with no keystroke at all is asserted by flipping the switch and waiting, and the companion assertion is that a change which flips nothing walks no root marker and spawns nothing — a negative claim, so it carries a positive twin in the same test, or it would also pass against a runtime that never subscribed. That the emptied server is stopped is asserted with `isProcessAlive` on the pid the platform really spawned, and its opposite is asserted by keeping a second language on the same process and showing the process untouched. The narrowings are not asserted twice: there is one implementation, so there is nothing to compare, and the existing reader tests are its specification.
